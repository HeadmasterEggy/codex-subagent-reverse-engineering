# Codex Subagent Reverse Engineering

Evidence-led notes on how Codex creates, coordinates, and reports subagents.

This repository contains a static-analysis report for the macOS Codex CLI embedded in ChatGPT and version-scoped comparisons with public Codex source tags. It does not include the Codex application or redistribute upstream source files.

## Current finding

The ChatGPT app embeds CLI `0.162.0-alpha.17.2`; its version-matched public source tag resolves to [`740e5af33c71225640e0c1c1555c514c2c93ab74`](https://github.com/openai/codex/tree/740e5af33c71225640e0c1c1555c514c2c93ab74). The separately installed standalone CLI reports `0.162.1` and is a different binary. The public `rust-v0.162.1` tag peels to [`092d3acd6bec3e3a14bdc7e7a2810ab628ab759d`](https://github.com/openai/codex/tree/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d). Neither version match proves exact binary build provenance.

In that source snapshot, V2 spawn creates a child thread through shared `AgentControl`, persists the parent-child edge before submitting the initial input, and delivers terminal outcomes through the V2 session event path. The detached completion watcher is the legacy route. See [the evidence report](evidence/subagent-flow.md).

The V2 `interrupt_agent` path sends `Op::Interrupt` to the selected thread only; a source fixture with a worker and grandchild asserts no interrupt or shutdown is sent to the grandchild. At the Session layer, interruption cancels the current turn, waits up to 100 ms for graceful exit before aborting the task, and can schedule a follow-up turn for pending trigger-turn mail or durable sleep. It does not itself close the thread. Tests were inspected, not run; see the [interruption scope and follow-up scheduling trace](evidence/subagent-flow.md#follow-up-v2-interrupt-targets-one-thread-and-may-start-pending-work).

A separate current-`main` source follow-up traces inherited environment selections into child startup and conditionally gated V2 capability discovery into MCP and world-state contribution contexts. Its integration test checks inventory projection without placing the sentinel skill string in model requests, but does not spawn a child; this is not evidence that V2-discovered skills become direct model-callable tools or that the installed Desktop uses current `main`. See the [version-scoped V2 discovery evidence](evidence/subagent-flow.md#current-main-v2-capability-discovery-metadata-and-child-step-projection).

A static inspection of the installed ChatGPT Desktop 26.1007.30912 bundle also confirms that its selected-subagent details header renders model and reasoning effort from the child thread's model-settings selector. The bundle maps that selector to `latestModel`/`latestReasoningEffort`, initialized from thread metadata. The inspection does not establish that V2 activity-item fields feed this selector, and it does not prove a live render; see [the scoped Desktop panel evidence](evidence/subagent-flow.md#installed-desktop-panel-renders-selected-child-model-settings).

The same installed bundle shows that conversation WebSocket events notify the desktop `localThreadCatalog` using `{hostId, conversationId}` and can trigger catalog refresh after reconnect. The main-process implementation maps those notifications to archive/unarchive catalog operations; this confirms a catalog synchronization bridge, not message-body ingestion into the app-server item store or the Work activity projection. See [the conversation socket/catalog trace](evidence/subagent-flow.md#installed-desktop-conversation-socket-notifies-the-local-thread-catalog).

Follow-up tracing shows that app-server catalog reads use `listThreads`/`readThread(includeTurns:false)`, while the ChatGPT catalog source maps `/conversations` metadata. Renderer catalog refresh updates thread metadata and recent summaries; its `mode:"catalog"` branch does not hydrate transcript turns. Separately, Work activity rows consume `vin`'s projection of the renderer conversation mapping, populated through history hydration and conversation WebSocket updates/refetches. The causal connection from that mapping to the app-server `item/started`/`item/completed` reducer remains unproven. See the [catalog trace](evidence/subagent-flow.md#installed-desktop-conversation-socket-notifies-the-local-thread-catalog) and [Work projection data path](evidence/subagent-flow.md#installed-desktop-work-projection-is-fed-by-the-renderer-conversation-mapping) for scoped evidence.

The Work response query's `activationId` is also resolved: `yin` derives it from the latest qualifying transcript message ID (spawn/send/resume, started/interacted activity, or pending/running per-agent state), retaining it across terminal activity and completed `wait`; otherwise it uses `initial:<threadId>`. This is a client query/cache discriminator, not evidence of a server-issued run ID. See [activation ID derivation](evidence/subagent-flow.md#work-response-query-activation-ids-are-transcript-message-ids).

The same Work projection schema-parses the two activity metadata records independently. A malformed non-null record is discarded without invalidating other valid records; if all are malformed, the selector still returns an empty projection. See [the metadata parser boundary](evidence/subagent-flow.md#invalid-work-activity-metadata-is-ignored-per-record).

The inline `chatgpt-subagent-activity` item emitted by the Work transcript projection is subsequently eligible for the renderer's generic `chatgpt-reasoning-group` projection on the ordinary conversation path. This confirms a nested transcript-projection step, not the final React renderer or visible UI; the streaming-parent projection follows a separate path. See [the reasoning-group projection trace](evidence/subagent-flow.md#work-inline-activity-items-enter-the-generic-reasoning-group-projection).

The installed conversation-turn renderer contains a dedicated React path for `chatgpt-subagent-activity`. In one Work-specific `kN` path, each inline item contributes its first activity as a parent activity unit while its compact summary receives the full activity list; the ordinary `wN` path renders the item directly through `fN`. Static component tracing resolves `pv` to `hk`: its unit renderer retrieves the matching inline summary by item ID and composes both in the activity section, which uses the parent activity collapse rules. Clicking a named summary entry opens or updates the parent-keyed Subagents panel tab with that child selected; the existing tab is reused for the same parent ID and the opener requests reveal/focus. This summary path does not branch on `canInteract`, unlike the separate child-avatar route. The selected panel detail uses a final-response query for done children and a status/preview branch for other states; this path does not enter the inspected interactive local-thread renderer. This is implementation evidence, not a captured live click or request. See [the inline activity renderer trace](evidence/subagent-flow.md#installed-conversation-renderer-has-a-dedicated-inline-subagent-activity-component), [the Work unit projection trace](evidence/subagent-flow.md#work-activity-renderer-creates-one-panel-unit-per-inline-activity-item), and [the summary selection route](evidence/subagent-flow.md#inline-work-activity-summary-selection-updates-the-parent-keyed-subagents-panel).

The Work `open-chatgpt-subagents-panel` opener registers no `durableRoute`; the inspected checkpoint path therefore omits that panel from route restoration. The separate local-conversation Subagents panel does register a versioned durable route and a dedicated restore handler, which restores the panel but clears the selected child for persistence restores. These findings apply to different panel entry points in the same installed bundle. See the [Work checkpoint trace](evidence/subagent-flow.md#the-work-subagents-panel-is-omitted-from-the-inspected-durable-tab-route-snapshot) and [local-conversation restore trace](evidence/subagent-flow.md#local-conversation-subagents-panel-registers-a-durable-route-and-restorer).

The local-conversation panel's overview rows are a merged projection: parent-thread activity items, discovered descendant snapshots, cached conversations and active thread summaries contribute memberships, then child turns and runtime metadata determine row state. Subscribing to the panel's descendant store triggers reconciliation and lifecycle subscriptions; opening the restored overview does not itself mean every child's transcript was hydrated. Selecting a child uses a separate ancestry/identity check and conditional history-loading path. In the matching app-server source, omitted `items_view` defaults to `Summary`, which keeps only the first user and last agent message and drops typed subagent activity/collaboration items. The installed selected-child transcript loader first locates turns with `notLoaded`, then explicitly hydrates a selected turn with `full` items; its adapter requests item pages of 30 and follows cursors until complete. A later renderer projection can still filter those items: it maps eligible collaboration/activity items to dedicated UI block types, subject to the background-subagent flag and projection budget, and omits `wait` actions. Additional installed resources trace the selected turn-entry props into the turn renderer, which calls the shared projection and explicitly handles `subagent-activity`; this establishes the renderer component path but not a React commit, DOM, or visible paint. The main local-conversation transcript reads a per-thread selector, defaults null to false, and passes it as `isBackgroundSubagentsEnabled`; tracing the ESM export alias and store writer shows that selector is backed by transcript `historyComplete` metadata. The page-level capability getter returns true but is not the value wired at this callsite. The upstream `historyComplete` value is computed from turn/item pagination and canonical-history completeness conditions; it is a history-loading predicate rather than a demonstrated subagent capability check. The component separately passes an `isConversationHistoryComplete` value to gate transcript projection, so the purpose of wiring history completeness under the subagent prop remains unresolved. The selected child's runtime value also remains unverified. See the [local panel data projection and child hydration trace](evidence/subagent-flow.md#local-conversation-subagents-overview-merges-membership-sources-and-hydrates-selected-children), [item-view boundary](evidence/subagent-flow.md#summary-item-view-omits-typed-subagent-events), [full item pagination](evidence/subagent-flow.md#selected-child-full-hydration-pages-all-items), [typed item renderer projection](evidence/subagent-flow.md#selected-child-full-items-pass-through-a-filtered-renderer-projection), and [selected-child renderer flag trace](evidence/subagent-flow.md#selected-child-renderer-flag-is-wired-to-transcript-history-completeness).

Following that component further identifies its summary layout and lifecycle mapping: up to three names are included in the sentence; larger groups show two names plus an overflow count, with compact activity chips. The status maps to active, updated, interrupted, completed, or failed from projected activity kinds/statuses. This remains static implementation evidence; no live DOM or click was captured. See [the component and status trace](evidence/subagent-flow.md#installed-inline-activity-component-summarizes-names-and-lifecycle-status).

A read-only correlation of the local Codex Desktop session store found three V2 parent-child rollout pairs for embedded CLI `0.162.0-alpha.17.2`. In each recorded sequence, the child's `task_started` precedes the parent's `SubAgentActivity(Started)`; at completion, `task_complete` precedes `Completed`, followed by the matching parent `agent_message`. This is a scoped observation of locally retained rollout records, not evidence of a global desktop default or exact UI render timing. No identifiers or message contents are published; see [the desktop runtime evidence](evidence/subagent-flow.md#desktop-research-session-runtime-metadata).

Matching each parent's `wait_agent` call to its recorded output adds an important boundary: two outputs mapped to `MailboxActivity`, one timed out; the matching parent `agent_message` followed the wait output in all three. In the two `MailboxActivity` pairs, the linked child's completion activity was recorded between the wait call and its output. The rollout does not identify which mailbox notification woke either handler. The timeout pair's child rollout contains multiple turns, so these records do not establish whether that wait output preceded completion of the specific child turn. This local sample does not make V2 `wait_agent` a child-join operation; see the detailed [wait timing evidence](evidence/subagent-flow.md#desktop-research-session-runtime-metadata).

Current-main source narrows the model-visible phrase "from any live agent": V2 `wait_agent` subscribes to the caller's own mailbox activity, while completion lifecycle activity and parent-directed result mail use separate routes. A caller wakes for messages that reach its mailbox; the tool does not subscribe to arbitrary descendants' status. The remaining wording ambiguity and exact source links are documented in [the current-main wait scope comparison](evidence/subagent-flow.md#current-main-wait_agent-wording-versus-mailbox-subscription-scope).

The 0.162.1 source snapshot also exposes structured agent-tree shutdown reporting: teardown failures are classified by operation and phase, retained up to 64 per tree, and include abandoned cleanup guards. It also conditionally preserves forked `AdditionalTools` declarations together with their context-comparison baseline. These are contrasts between public source snapshots, not proof of a linear version transition or the introducing commit; this checkout was shallow when ancestry was checked. They are source evidence, not live observations from the ChatGPT desktop host.

Further tracing shows that sender evidence is a required shared Guardian section: an insufficient context budget fails closed, and recording a newer sender delivery changes the review revision so an in-flight approval becomes stale (unless cancellation or root-history reset aborts first). See [review-context admission and invalidation](evidence/subagent-flow.md#follow-up-sender-evidence-is-required-reviewer-context-and-invalidates-stale-review-authorization).
That stale result is retried using fresh revision snapshots under the same deadline; if it remains stale or expires, Guardian returns a failed-closed denial and rolls back the uncommitted reviewer checkpoint. See [stale-review retry and completion](evidence/subagent-flow.md#follow-up-stale-approval-reviews-retry-on-fresh-evidence-then-fail-closed).

V2 `followup_task` can wake an idle child; `send_message` queues without waking an idle child. Both ultimately feed the child mailbox, and accepted submission does not prove model consumption. See [message delivery and turn scheduling](evidence/subagent-flow.md#follow-up-v2-follow-up-messages-are-admitted-to-mailbox-input-not-guaranteed-model-consumption).

The parent's `Interacted` activity records accepted contact; the child's own `TurnStarted` is the signal that its next turn actually began. Ordinary interruption does not emit a completion result, while Guardian's repeated-denial stop sends the parent a specific no-retry-without-user-confirmation message. Completion/error results use QueueOnly delivery; an unloaded parent can receive one later from the same runtime's in-memory mailbox, which does not provide a cross-restart delivery guarantee. See the [status lifecycle](evidence/subagent-flow.md#follow-up-child-status-returns-to-running-on-turnstarted-parent-activity-uses-interacted), [terminal outcome rules](evidence/subagent-flow.md#follow-up-v2-result-delivery-skips-ordinary-interruption-and-escalates-guardian-stops), and [unloaded-parent delivery boundary](evidence/subagent-flow.md#follow-up-result-mail-to-an-unloaded-parent-is-only-retained-in-the-live-runtime-mailbox).

Work inline activity blocks group only contiguous, schema-valid activity/tool-call contributions with the same renderer turn key, then attach the reduced block to the run's final transcript message. Invalid metadata and ordinary messages break a run; the Work panel's overall child rows are a separate output of the same reducer. See [the inline activity grouping trace](evidence/subagent-flow.md#work-activity-blocks-group-contiguous-metadata-contributions-by-turn).

An installed ChatGPT Desktop `26.1007.71326` (build `20398`) follow-up revalidated the local panel path in a newer app bundle. Its selected-child opener checks the ancestry chain, rejects cycles and known host mismatches, guards against stale async tab selections, and conditionally hydrates parent/child history; the separate Work panel final-response query requests one turn and prefers a non-empty `final_answer` message. REA parsed four caller-selected resources from the exact ASAR, leaving 16,236 inventoried files outside this analysis. This is static code evidence, not a live UI or request capture. The ASAR also contains native integrity contradictions; see [the versioned bundle record](evidence/subagent-flow.md#installed-desktop-26100771326-selected-child-panel-path). A further static trace of the same build found that the local Subagents panel combines typed parent-history items, indexed child threads, cached conversations, and a descendant-discovery snapshot to derive its child rows. A full-ASAR REA run parsed all 15,211 JavaScript files it classified, with zero parse failures, but its semantic graph remained partial: result-budget limits prevented semantic projection of both subagent bundles. The exact panel data path therefore remains supported by direct inert source inspection; the full-bundle run independently confirms file presence and syntax parsing, not a complete relationship graph or live behavior. See [the panel projection and full-ASAR coverage limits](evidence/subagent-flow.md#full-asar-static-parse-coverage-and-semantic-projection-limits).

A 2026-10-15 selected-resource trace distinguishes the two installed panel implementations: the Codex local-conversation panel opens the selected child through the local transcript owner, which hydrates metadata and conditionally reads/paginates turns through the thread/read and thread/turns/list RPCs, while the Work panel separately queries /flora/subagent/thread/turns for one child turn and prefers a non-empty final_answer message. ## Reproduce local identity checks

On macOS with the same app installed:

```sh
./scripts/collect-macos-evidence.sh
```

The script reads the executable, prints its version, SHA-256, Mach-O UUID, and selected symbol/string matches. It does not start an agent session or modify the app. Pass an executable path as the first argument to inspect a different installation.

## Evidence boundaries

- A 2026-10-15 trace at upstream `835cd7552d6a089bbdfeb21b001cb76c503249c7` confirms that follow-up caller identity reaches the child turn through `InterAgentCommunication.author`, even when `TurnStartOptions.initiating_agent_path` is omitted. Completion can send the initiator a lifecycle event, but `wait_agent` listens to mailbox/steer queue activity; the final result remains addressed to the structural parent. This separates UI/lifecycle attribution from mailbox delivery and does not itself reproduce #32203; see the [current-main attribution trace](evidence/subagent-flow.md#current-main-follow-up-attribution-does-not-turn-lifecycle-activity-into-mailbox-input).

- Static symbols and strings establish that named code/data is present, not that a particular runtime path executed.
- Disassembly is interpreted narrowly and cross-checked against the versioned public source where possible.
- A matching version tag is not a signed build-provenance statement.
- Live CLI evidence now includes one successful single-child probe and four controlled nested V2 runs on standalone CLI `0.162.1`. In the natural-completion run, both waits completed without timeout; the child received the grandchild result, then the root received the child's summary and no direct grandchild result. In the direct-grandchild-follow-up runs, a root wait timed out both when started after the grandchild's `Completed` activity and when already pending as that activity arrived. In the pending case, the root wait began at `12:30:34.960Z`, the activity arrived at `12:30:44.105Z`, and the wait timed out at `12:31:35.084Z`; the grandchild's result remained routed to its direct parent. A separate mailbox control showed that an explicit grandchild `send_message` to root made its pending wait return `timed_out:false` within milliseconds. These scoped runs are not Desktop conversation-host reproductions. A separate ephemeral probe failed because no parent rollout was found. No network capture or private server-side implementation analysis is included.
- The cross-ancestor follow-up/wait behavior matches the failure mode reported in [upstream issue #32203](https://github.com/openai/codex/issues/32203). A read of upstream `main` at `7a08c5f6271e818d832eb9061dac935936e2b539` on 2026-10-14 found the same routing contract in the relevant public source: path resolution accepts a registered descendant, `followup_task` records the initiating turn, completion sends the result to the target's spawn-time parent, and `wait_agent` subscribes to the caller's own queue. This establishes that the inspected source still has the reported route shape; it does not prove the exact cause of any hosted Desktop report. [Issue #15723](https://github.com/openai/codex/issues/15723) is related but distinct: it reports intermittent direct-child/idle-parent completion wake behavior.
- The inspected current-main unit and integration tests cover root-target rejection from a child, direct-parent follow-up completion, and mailbox-based parent waits; I found no assertion for the cross-ancestor `followup_task(grandchild)` followed by root `wait_agent` sequence in those relevant files. This is a bounded test-source scan, not a repository-wide coverage claim and not a test run; see the [test-coverage boundary](evidence/subagent-flow.md#current-main-test-coverage-boundary).

## Versioned source path

The public source tag exactly matches the CLI's reported version. In that snapshot:

1. The V2 tool handler builds a `ThreadSpawn` source and sends a `SpawnRequest` to `AgentControl`.
2. `spawn_agent_internal` selects the effective multi-agent version, admits the start, checks capacity, reserves registry/residency slots, and prepares inherited environment/execution policy and metadata.
3. The controller creates the child thread (or forked thread), records the spawn edge, waits for persistence, then submits the first input.
4. On `TurnComplete` or `TurnAborted`, a V2 session constructs an `AgentTurnOutcome` and calls `turn_finished`.
5. Completion routing may emit a `Completed` activity to the initiating thread and queues an inter-agent result communication with `trigger_turn = false`.
6. The parent queue receiving a message and the parent model processing it are separate events.

The older watcher accepts only a `ThreadSpawn` source with a structural parent and only starts while the shared agent-tree runtime admits new work. Its status stream emits an initial snapshot, then coalesced watch-channel updates; it subscribes before reading thread settings so it does not miss an intervening status change. If subscription setup fails or the stream ends/errors before a terminal status is observed, it calls `get_status` once. Final statuses are `Completed`, `Errored`, `Shutdown`, and `NotFound`; `PendingInit`, `Running`, and `Interrupted` are non-final. A tree-shutdown cancellation exits the select, and a `Shutdown` result is suppressed when that same tree shutdown is in progress. Other final results are routed to the structural parent: when an agent path exists and the child is V2, the watcher sends a result communication with `trigger_turn = false`; otherwise it injects `SubagentNotification` without starting a parent turn. Missing parent state or failed path/message construction ends delivery; the V2 send result is intentionally ignored. The watcher holds an agent-tree teardown guard, and an abnormal drop before `complete()` records a shutdown failure. Fresh and resumed spawn callsites both start it only when the effective version is not V2. Sources: [`control.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs), [`control/watch.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/watch.rs), [`status.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/status.rs), [`control/runtime.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/runtime.rs), and [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs). This is source-derived behavior; no runtime watcher event was captured.

### Same-tag app-server and state database path

The same source tag also defines the local `thread/list` relation filter. `parentThreadId` and `ancestorThreadId` are mutually exclusive and become direct-child or descendant filters; the app-server passes them through the thread store. The state DB implements descendant lookup with a recursive SQLite CTE over `thread_spawn_edges`, then joins those child IDs to stored threads. `sourceKinds: [SubAgentThreadSpawn]` is mapped to a post-filter over the stored session source. The selected source path's child edge is upserted in the local agent graph store unless the child is ephemeral, and the spawn controller waits for the edge-write task before sending the child's first input. This links edge persistence to the source-level spawn sequence and explains the client bundle's efficient ancestor query. It remains evidence about the matching public source tag; it does not prove this local ChatGPT app's backend process is byte-for-byte from that commit.

Sources: [`thread_processor.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/app-server/src/request_processors/thread_processor.rs), [`state/src/runtime/threads.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/state/src/runtime/threads.rs), [`thread-store/src/local/list_threads.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/thread-store/src/local/list_threads.rs), [`control.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs), [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs), and [`0021_thread_spawn_edges.sql`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/state/migrations/0021_thread_spawn_edges.sql).

The persisted edge lifecycle has only `open` and `closed`: open means the child is still live or resumable in the spawn graph. Explicit `close_agent` marks the edge closed before shutdown; `shutdown_live_agent` intentionally does not. Thus edge state is not the same field as the UI's working/done/failed status, and a shutdown operation alone does not imply graph closure.

### Parent result delivery after child termination

In the same source tag, V2 terminal handling has two parent-facing effects with different conditions. A successful child emits `SubAgentActivityKind::Completed` only when its outcome has a `parent_turn_id`; the result communication is then built separately for the parent agent path. The result message has `trigger_turn = false`, so delivery does not by itself start an idle parent turn.

For a loaded parent, the controller submits `Op::InterAgentCommunication` to the session. The session enqueues it in its mailbox and lets the shared pending-work scheduler decide whether to start work; for `trigger_turn = false`, an ordinary idle session is not automatically started. Mailbox delivery can still be accepted into the current active turn while that turn accepts mailbox input. Otherwise the item remains pending and can be collected into later turn input. For an unloaded parent, the controller queues the communication in the local runtime mailbox; the next loaded session takes those messages into its own input queue. Accordingly, successful queue submission proves delivery was accepted or retained, not that the parent model has already consumed the result.

When a parent turn processes the queued `TurnInput::InterAgentCommunication`, the hook path calls `Session::record_inter_agent_communication`. `InterAgentCommunication::to_model_input_item` converts it to a typed `ResponseItem::AgentMessage` carrying author, recipient, and content; the session prepares and records that item in conversation history/rollout and emits the response item. This establishes the source-level handoff from mailbox to model-visible conversation context, while still not proving that a particular live model request sampled that item. Sources: [`hook_runtime.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/hook_runtime.rs), [`session/mod.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/mod.rs), and [`protocol.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/protocol/src/protocol.rs).

The result content is formatted from terminal status: successful output, an error message with bounded error text and next-step guidance, or shutdown/not-found wording; pending, running, and interrupted statuses produce no generic completion message. Special Guardian denial outcomes use a separate instruction. Sources: [`completion.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/completion.rs), [`control.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs), [`mailbox.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/mailbox.rs), [`handlers.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/handlers.rs), and [`input_queue.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/input_queue.rs).

### `send_message` versus `followup_task`

Both V2 tools use one shared handler that rejects whitespace-only messages, resolves the target to a thread ID, builds a resume config from the caller's current turn, sends an `AgentInput::Message`, and emits an `Interacted` activity after the send succeeds. The difference is the delivery mode: `send_message` selects `QueueOnly`, while `followup_task` selects `TriggerTurn`. The target resolution accepts a thread ID directly or resolves an agent reference in the caller's session source. Sources: [`message_tool.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/message_tool.rs), [`send_message.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/send_message.rs), [`followup_task.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/followup_task.rs), and [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs).

For a loaded target, `QueueOnly` submits ordinary inter-agent communication without the trigger flag. The session handler enqueues it and does not ask the pending-work scheduler to start a turn unless the target has an outstanding durable sleep. For an unloaded target, the controller retains queue-only mail in a runtime mailbox; later session loading drains it into the session queue. By contrast, `TriggerTurn` ensures the V2 target is loaded, marks plaintext communication as `NewTask` (or sets the trigger flag on encrypted communication), checks turn-start capacity, and asks the session scheduler to start a regular turn when pending mailbox work is present and the session is idle. Triggered delivery to the root agent is explicitly rejected. Sources: [`delivery.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/delivery.rs), [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs), [`control.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs), [`handlers.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/handlers.rs), and [`tasks/mod.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tasks/mod.rs).

Trigger delivery to an unloaded child uses the existing thread identity and stored history/rollout to resume a V2 session; it does not call the spawn path to create a replacement child. The restore path rejects non-V2 history. If a parent is supplied as owner, it validates that parent is still running, belongs to the same runtime registry, and matches the child's recorded parent; the sender-driven message path passes no parent object and instead restores from the child source and stored configuration/history. Sources: [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs) and [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs).

These paths establish submission and wake policy, not immediate consumption: a queued message can wait for a later turn, and an `Interacted` activity is emitted after accepted delivery rather than after the target model has read the message. This is source-derived behavior for the matching tag; no live child was messaged in this investigation.

### V2 interruption is not closure

The V2 `interrupt_agent` handler snapshots the target first, asks the controller to interrupt it, returns the snapshot's prior status, and emits an `Interrupted` activity. The V2 controller rejects the root and self-targets. If the child runtime is unloaded or already dead, thread-not-found/internal-agent-died errors from the interrupt dispatch are treated as success; this path does not reload the target. It does not mark the persisted spawn edge closed or remove the agent from the registry. In contrast, `close_agent` explicitly marks the edge closed and shuts down the target plus currently live descendants; ordinary shutdown removes runtime/registry/mailbox state but intentionally does not itself close the persisted edge. A later `followup_task` takes the trigger-turn path and ensures the V2 target is loaded before delivery. Sources: [`interrupt_agent.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/interrupt_agent.rs), [`control/interrupt.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/interrupt.rs), [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs), [`control/legacy.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/legacy.rs), and [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs). This is a static source distinction; no interrupt/restart experiment was run.

### `list_agents` is a loaded-runtime view

The V2 handler returns agent path/name and status, with an optional prefix resolved relative to the caller's agent path. The controller gathers metadata from the in-memory agent registry, then includes an entry only if its thread is currently present in the thread manager; known but unloaded agents are skipped, and a root entry is likewise added only when its thread is loaded. The app UI's separate persisted `thread/list` and history-discovery paths therefore have broader historical coverage than this tool result. ### Spawn admission and rollback

The V2 spawn path applies more than one resource check. `ensure_execution_capacity` checks the V2 subagent turn-execution limiter; actual turn admission obtains a separate RAII execution guard, held for the admitted task's lifetime. The limiter is initialized from the session's effective V2 agent max-thread setting. Spawn also reserves a registry slot. For V2 resident child sources it first reserves a V2 residency slot and does not pass the ordinary registry max-thread limit to `reserve_spawn_slot`; other spawn paths pass their effective agent max-thread limit to the registry. These controls therefore describe different resources and should not be collapsed into one concurrency limit. ## V2 child cold-resume configuration

`ensure_v2_agent_loaded` has two materially different resume callers. Both require registered child metadata, a readable stored thread, loadable model-context history, and a resumed history marked V2. They reuse the existing thread ID and rollout; they do not create a replacement child. A caller that supplies the live parent additionally has to prove that the parent is still the same registered running V2 thread in the same runtime registry, and that source/history/stored parent IDs agree.

With a live parent, resume configuration is rebuilt from a fresh parent turn. The child’s stored reasoning effort and stored model/provider are then restored; a saved agent role is reapplied while the current runtime approval policy, cwd, and permission-profile snapshot are preserved. The controller rejects a changed parent execution policy. Cached environment selections must match a currently ready parent environment by environment ID, cwd, and workspace roots. Pending/failed selections are rejected; config differences are rejected after substituting the current owner permission profile. For local executors, a differing cached permission profile is intersected with current owner authority; a remote executor with changed permissions is rejected. This is a constrained resume, not blind restoration of the child’s old authority.

The sender-driven `send_message`/`followup_task` path passes no live parent object to the loader. It retains the supplied resume config, restores stored child model/provider/reasoning, and attempts to inherit environment and execution-policy handles by following the saved `ThreadSpawn` parent source if that parent is loaded. The exec-policy handle is inherited only if the parent/child policy compatibility predicate still passes. This path supplies no `client_mcp_extensions` from a parent object. Parent instructions come from a loaded parent when available, otherwise from the shared thread-instructions provider. Therefore “cold resume” alone does not identify one configuration policy; caller path and which parent/runtime state is available matter.

Sources: [`ensure_v2_agent_loaded`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs), [`inherited_environments_for_source` and `inherited_exec_policy_for_source`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs). ## Multi-agent version selection

In the inspected tag, a configured `features.multi_agent_v2` override selects V2. An explicit global agent disable selects Disabled; otherwise the config override is absent. For a spawned thread, the controller next attempts to inherit the version from its parent/source or the resumed/forked history, and only then falls back to feature configuration (`collab` => V1, otherwise Disabled). Resumed history created before version metadata existed is treated as V1. At turn setup, model metadata can also supply a version when no thread version is already set, but explicit config override takes precedence; the session then records its selected version.

## Interrupted status, completion, and residency

The V2 status mapper classifies both an explicit interrupt abort and a budget-limited abort as `Interrupted`. This status is deliberately non-final for status-wait logic, and completion-message formatting returns no ordinary completion message for `Interrupted`. By contrast, a completed turn can emit a `Completed` activity and a separate queue-only result message. Thus an interrupted child is not equivalent to a completed child whose result is empty.

Residency uses a separate predicate: `Completed`, `Errored`, and `Interrupted` are all unloadable when there is no active turn, durable sleep, or trigger-turn mailbox item. “Not final” therefore does not mean “must stay resident.” Manual interrupt also does not close the persisted spawn edge; a later trigger-turn follow-up can reload the same V2 child if its history and current resume checks pass. These statements describe different state surfaces—agent status, completion delivery, in-memory residency, and graph-edge lifecycle—and should not be collapsed into one done/running label.

### SubagentTopology static path

The extracted `app-shared` bundle exposes a store facade: `getSubagentDescendantSnapshot(parentId)` returns currently known descendants, `isComplete: false`, and an `isLoading` flag based on in-flight discovery. Discovery is separate and can reconcile its result with a snapshot of runtime status captured before the asynchronous reads. Full-subtree and direct-child discovery use separate in-flight maps and reuse matching work.

- With thread-list filters supported, discovery queries `thread/list` for `sourceKinds: ["subAgentThreadSpawn"]`, `archived: false`, `sortKey: "created_at"`, descending, `limit: 200`, and `useStateDbOnly: true`. At app-server versions at least `0.143.0-alpha.16`, it uses `ancestorThreadId`; on older versions, it queries each `parentThreadId` and walks descendants. Paging stops at the parent's creation-time boundary and repeated cursors make the result incomplete.
- Without thread-list filters, observed spawn IDs are supplemented from history. `thread/items/list` extracts `subAgentActivity(started)` and `collabAgentToolCall(spawnAgent)` IDs. For a paginated-history thread not yet cached, `thread/turns/list` is scanned page by page to reconstruct child IDs from turn items.
- Candidate children not already known are loaded with `thread/read(includeTurns: false)`. A result is accepted only if its ID matches the requested child and its parent matches the current node. At most two children are fetched concurrently. Failures, identity mismatches, or incomplete nested-history reads preserve `isComplete: false`.
- When a spawn event identifies exactly one child already in the store with a matching parent, the app first hydrates that child in the background and discovers its subtree. Otherwise it falls back to discovering the parent's full descendant set.
- The runtime item-event path calls `discoverForSpawn` when it receives `collabAgentToolCall(spawnAgent)` or `subAgentActivity(started)`. This is an event-driven discovery trigger distinct from the UI's read of the current store snapshot; static code does not establish that opening the panel always launches a fresh query.

These are client-side static observations. The bundle does not reveal server persistence, filtering implementation, authorization, or whether each host uses the same route. `isComplete` describes discovery coverage in this client algorithm; it is not evidence that all remotely existing subagents are known.

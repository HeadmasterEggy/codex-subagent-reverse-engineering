The Codex composer adapter wraps and passes that callback, and the session component supplies its stop handler. For a local composer, the handler uses the current resolved host when no explicit conversation ID is supplied; when an ID is supplied, it looks up that conversation's host in the app store. This is not the `beforeArchiveConversation` callback and it does not call `stopThread`. The archive path may converge internally only when `stopThread` falls back from durable `thread/stop` to `interruptConversation`. The selected manager's `user-stop` path can schedule subagent-descendant interruption in the background; this is best-effort cleanup, and the interrupt result or expected-turn guard can affect whether the cascade starts. This is a bundle-level static call graph: no button was clicked and no runtime routing was observed. The Stop control is rendered only when the composer state selects the `stop` submission mode. ### Shutdown request API and ownership boundary (0.162.1 source)

The new public `ThreadManager::request_agent_tree_shutdown(thread_id)` first resolves a **loaded** thread, then closes the exact local runtime's `TaskTracker` admission fence, cancels its shared tree token, closes its mailboxes, and returns an `AgentTreeShutdown` handle. `wait()` and `wait_detailed()` wait until all members admitted before the fence have drained. `admit_start()` checks the closed fence both before and after acquiring a tracker token, so a concurrent start is either tracked by the wait or rejected with `RuntimeShutdown`.

The membership sites inspected cover session startup/session loop, fresh child spawn, agent resume, V2 child loading, legacy completion watcher, resident eviction, and some inter-agent delivery operations. Startup cancellation retains membership until it has stopped session I/O or shut down a partially built session and discarded uncommitted persistence. Teardown guards record abandoned cleanup; detailed reports retain at most 64 failures and count the rest. The ordinary `wait()` surface collapses the report into a generic fatal error; `wait_detailed()` exposes the bounded structured report.

The API explicitly leaves registry removal and caller-owned persistence handoff to its caller. It only fences starts that share the current local runtime; top-level loads/resumes of the same thread ID outside that runtime must be serialized separately. Subagent creation passes the parent's same `LocalAgentRuntime` into the child, so targeting a loaded child ID with this API would resolve the shared runtime and fence the root and its same-runtime siblings too; it is not a child-subtree-only handle. This runtime-wide fence is distinct from `close_agent`: the latter marks the target spawn edge closed and walks the target plus live descendants, shutting them down individually. The inspected app-server idle-thread unload is a third path: it calls `CodexThread::shutdown_and_wait()` for one thread, then removes that same runtime with `remove_thread_if_matches`. A read-only search of the 0.162.1 source found no internal production call site for `request_agent_tree_shutdown` beyond its definition. Thus this tag proves a host/SDK-facing shutdown mechanism exists, not that the ChatGPT desktop invokes it for subagents. This is source inspection only; the API and race behavior were not exercised live. Sources: [`thread_manager/shutdown.rs`](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/thread_manager/shutdown.rs#L105-L147), [`agent/control/runtime.rs`](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/agent/control/runtime.rs#L274-L302), [`codex_delegate.rs`](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/codex_delegate.rs#L81-L130), [`session/startup.rs`](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/session/startup.rs#L32-L105), [`close_agent`](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/agent/control/legacy.rs#L48-L123), and [app-server idle unload](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L419-L489).

## Additional finding: spawn tool result identity

The V2 `spawn_agent` success result serializes `task_name` and optionally `nickname`; it does not serialize the child `ThreadId`. The handler and started-activity path retain the actual child thread ID separately, and `SubAgentActivityEvent` has both `agent_thread_id` and canonical `agent_path`. The source default hides spawn metadata, which removes the optional nickname from the tool result. This distinguishes the model-facing result from internal activity identity; it does not establish what a particular UI renders. Sources: [`multi_agents_v2/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs), [`config/mod.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/config/mod.rs), and [`protocol.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/protocol/src/protocol.rs).

The controller waits for spawn-edge persistence and initial input admission, commits reservations, and returns the live agent before the V2 handler emits the `Started` activity. Thus `Started` is evidence of successful control-plane creation/input admission in this source path, not evidence that the child has begun model inference. Actual execution permit acquisition belongs to later scheduling. Sources: [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs) and [`multi_agents_v2/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs). This is static source ordering, not a live timing measurement.

## Additional finding: V1 and V2 expose different spawn identities

In the same source tag, the V1 spawn handler returns `agent_id` as the child thread ID string, plus an optional nickname. It also emits a `CollabAgentToolCall` turn item before and after spawn with sender/receiver thread IDs, prompt, model, reasoning effort, and agent status. The V1 `wait_agent.targets` contract can therefore consume the ID returned by V1 spawn. V2 instead returns a normalized `task_name`; its child thread ID stays in internal handler/activity structures. Do not interchange the V1 ID and V2 task name. This is a source-contract comparison and does not establish which fields a particular desktop UI displays. Source: [`V1 spawn handler`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents/spawn.rs), [`V1 wait handler`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents/wait.rs), and [`V2 spawn handler`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs).

## Additional finding: V2 spawn handler exists in the installed machine code

The installed arm64 Mach-O retains the Rust symbol for `multi_agents_v2::spawn::Handler::handle` at `0x105083d2c`. Targeted `otool -arch arm64 -tvV -p <mangled-symbol>` disassembly shows call instructions at `0x1050846d0`, `0x1050848c4`, `0x105085184`, and `0x105085204`, whose resolved symbol names are respectively `multi_agents_common::thread_spawn_source`, `session::multi_agents::resolve_usage_hints`, `record_collab_spawn_failure`, and `collab_spawn_error`. This is direct local machine-code evidence that the installed binary contains a V2 spawn handler wired to these named helpers. Symbol names and call sites do not by themselves prove every helper's behavior or that this exact binary was built from the matching public tag. The disassembly was inspected locally and is not a captured live spawn.

Reproduce the symbol lookup and focused disassembly on the same binary with:

```sh

```

## Live CLI probe

On 2026-10-13, one controlled CLI run used the embedded binary with `exec`, `--enable multi_agent_v2`, `--ignore-user-config`, `--sandbox read-only`, `--skip-git-repo-check`, and `/tmp` as cwd. The parent was asked to spawn one child with a fixed response, wait for it, and avoid other tools or file access. The persisted rollout records `multi_agent_version: v2`; `spawn_agent` returned only `{"task_name":"/root/probe_child"}`. The parent then emitted `SubAgentActivity` items of kind `started` and `completed` for that path, and called `wait_agent`, which returned `Wait completed.` with `timed_out: false`. A separate child rollout records `thread_source: subagent`, a `thread_spawn` source with parent linkage and depth 1, and final text `CHILD_PROBE_OK`. The parent received a typed `AgentMessage` from `/root/probe_child` with that result. This is one successful live CLI run, not a desktop conversation trace or evidence that the default desktop configuration selects V2.

An otherwise equivalent `--ephemeral` attempt did not create a child: the parent turn reported `spawn_agent failed because no rollout was found for the thread`, and no child result was available. This indicates that the tested spawn path needs a persisted rollout for the parent. It does not establish whether every ephemeral mode or host has the same constraint. Neither run read or modified project files; the successful run created normal parent and child session records under the user's Codex session store.

A follow-up fresh `exec` probe passed `--ignore-user-config --enable multi_agent --disable multi_agent_v2` and requested one fixed-response child. The same embedded CLI's `features list --disable multi_agent_v2` reported V2 `false`, and `debug models` reported the `gpt-6.1-sol` entry as `v1`. Yet this new run's rollout `turn_context` recorded `multi_agent_version=v2`; its `spawn_agent` call returned the V2-shaped `task_name`, and the child completed. In the matching source, `multi_agent_version_for_model` first honors the V2/Disabled config override, then uses the current turn's `ModelInfo.multi_agent_version`, then falls back to feature selection. Disabling `multi_agent_v2` cancels the config's V2 override; it does not force Disabled or V1 while agents remain enabled.

The source also narrows the measurement mismatch. `codex debug models` constructs its own config and model manager, then prints that manager's `raw_model_catalog`. A session instead asks its model manager for the active catalog, matches candidates against the turn's model slug, constructs `ModelInfo`, and applies config overrides. The source `with_config_overrides` function does not modify `multi_agent_version`. These are separate command/session contexts, so the debug output is not proof of the exact metadata snapshot consumed by the turn. A metadata-only read of the local cache found `gpt-6.1-sol` marked `v1`, with `fetched_at=2026-10-13T10:35:56Z`; the probe rollout began at `10:28:48Z`, so this cache snapshot post-dates the probe. The matching source declares a 300-second default cache TTL. This later snapshot does not reveal the catalog held in the probe session. The source supports independent catalog/context as a possible explanation, but the actual candidate metadata for this probe was not captured; the specific cause remains unknown. Sources: [`debug models` implementation](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/cli/src/main.rs#L2093-L2121), [`get_model_info`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/models-manager/src/manager.rs#L212-L224), [`ModelInfo` config overrides](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/models-manager/src/model_info.rs#L19-L58), [`resolve_multi_agent_version_for_model`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/mod.rs#L4019-L4031), and [`multi_agent_version_for_model`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/config/mod.rs#L1487-L1512). ## Versioned source path

The public source tag exactly matches the CLI's reported version. In that snapshot:

1. The V2 tool handler builds a `ThreadSpawn` source and sends a `SpawnRequest` to `AgentControl`.
2. `spawn_agent_internal` selects the effective multi-agent version, admits the start, checks capacity, reserves registry/residency slots, and prepares inherited environment/execution policy and metadata.
3. The controller creates the child thread (or forked thread), records the spawn edge, waits for persistence, then submits the first input.
4. On `TurnComplete` or `TurnAborted`, a V2 session constructs an `AgentTurnOutcome` and calls `turn_finished`.
5. Completion routing may emit a `Completed` activity to the initiating thread and queues an inter-agent result communication with `trigger_turn = false`.
6. The parent queue receiving a message and the parent model processing it are separate events.

The older watcher accepts only a `ThreadSpawn` source with a structural parent and only starts while the shared agent-tree runtime admits new work. Its status stream emits an initial snapshot, then coalesced watch-channel updates; it subscribes before reading thread settings so it does not miss an intervening status change. If subscription setup fails or the stream ends/errors before a terminal status is observed, it calls `get_status` once. Final statuses are `Completed`, `Errored`, `Shutdown`, and `NotFound`; `PendingInit`, `Running`, and `Interrupted` are non-final. A tree-shutdown cancellation exits the select, and a `Shutdown` result is suppressed when that same tree shutdown is in progress. Other final results are routed to the structural parent: when an agent path exists and the child is V2, the watcher sends a result communication with `trigger_turn = false`; otherwise it injects `SubagentNotification` without starting a parent turn. Missing parent state or failed path/message construction ends delivery; the V2 send result is intentionally ignored. The watcher holds an agent-tree teardown guard, and an abnormal drop before `complete()` records a shutdown failure. Fresh and resumed spawn callsites both start it only when the effective version is not V2. Sources: [`control.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs), [`control/watch.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/watch.rs), [`status.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/status.rs), [`control/runtime.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/runtime.rs), and [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs). ### Same-tag app-server and state database path

The selected source path's child edge is upserted in the local agent graph store unless the child is ephemeral, and the spawn controller waits for the edge-write task before sending the child's first input. ### Parent result delivery after child termination

In the same source tag, V2 terminal handling has two parent-facing effects with different conditions. A successful child emits `SubAgentActivityKind::Completed` only when its outcome has a `parent_turn_id`; the result communication is then built separately for the parent agent path. The result message has `trigger_turn = false`, so delivery does not by itself start an idle parent turn.

For a loaded parent, the controller submits `Op::InterAgentCommunication` to the session. The session enqueues it in its mailbox and lets the shared pending-work scheduler decide whether to start work; for `trigger_turn = false`, an ordinary idle session is not automatically started. Mailbox delivery can still be accepted into the current active turn while that turn accepts mailbox input. Otherwise the item remains pending and can be collected into later turn input. For an unloaded parent, the controller queues the communication in the local runtime mailbox; the next loaded session takes those messages into its own input queue. Accordingly, successful queue submission proves delivery was accepted or retained, not that the parent model has already consumed the result.

When a parent turn processes the queued `TurnInput::InterAgentCommunication`, the hook path calls `Session::record_inter_agent_communication`. `InterAgentCommunication::to_model_input_item` converts it to a typed `ResponseItem::AgentMessage` carrying author, recipient, and content; the session prepares and records that item in conversation history/rollout and emits the response item. This establishes the source-level handoff from mailbox to model-visible conversation context, while still not proving that a particular live model request sampled that item. Sources: [`hook_runtime.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/hook_runtime.rs), [`session/mod.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/mod.rs), and [`protocol.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/protocol/src/protocol.rs).

Special Guardian denial outcomes use a separate instruction. ### `send_message` versus `followup_task`

Both V2 tools use one shared handler that rejects whitespace-only messages, resolves the target to a thread ID, builds a resume config from the caller's current turn, sends an `AgentInput::Message`, and emits an `Interacted` activity after the send succeeds. The difference is the delivery mode: `send_message` selects `QueueOnly`, while `followup_task` selects `TriggerTurn`. The target resolution accepts a thread ID directly or resolves an agent reference in the caller's session source. Sources: [`message_tool.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/message_tool.rs), [`send_message.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/send_message.rs), [`followup_task.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/followup_task.rs), and [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs).

For a loaded target, `QueueOnly` submits ordinary inter-agent communication without the trigger flag. The session handler enqueues it and does not ask the pending-work scheduler to start a turn unless the target has an outstanding durable sleep. For an unloaded target, the controller retains queue-only mail in a runtime mailbox; later session loading drains it into the session queue. By contrast, `TriggerTurn` ensures the V2 target is loaded, marks plaintext communication as `NewTask` (or sets the trigger flag on encrypted communication), checks turn-start capacity, and asks the session scheduler to start a regular turn when pending mailbox work is present and the session is idle. Triggered delivery to the root agent is explicitly rejected. Sources: [`delivery.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/delivery.rs), [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs), [`control.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs), [`handlers.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/handlers.rs), and [`tasks/mod.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tasks/mod.rs).

Trigger delivery to an unloaded child uses the existing thread identity and stored history/rollout to resume a V2 session; it does not call the spawn path to create a replacement child. The restore path rejects non-V2 history. If a parent is supplied as owner, it validates that parent is still running, belongs to the same runtime registry, and matches the child's recorded parent; the sender-driven message path passes no parent object and instead restores from the child source and stored configuration/history. Sources: [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs) and [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs).

These paths establish submission and wake policy, not immediate consumption: a queued message can wait for a later turn, and an `Interacted` activity is emitted after accepted delivery rather than after the target model has read the message. This is source-derived behavior for the matching tag; no live child was messaged in this investigation.

### V2 interruption is not closure

The V2 `interrupt_agent` handler snapshots the target first, asks the controller to interrupt it, returns the snapshot's prior status, and emits an `Interrupted` activity. The V2 controller rejects the root and self-targets. If the child runtime is unloaded or already dead, thread-not-found/internal-agent-died errors from the interrupt dispatch are treated as success; this path does not reload the target. It does not mark the persisted spawn edge closed or remove the agent from the registry. In contrast, `close_agent` explicitly marks the edge closed and shuts down the target plus currently live descendants; ordinary shutdown removes runtime/registry/mailbox state but intentionally does not itself close the persisted edge. A later `followup_task` takes the trigger-turn path and ensures the V2 target is loaded before delivery. Sources: [`interrupt_agent.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/interrupt_agent.rs), [`control/interrupt.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/interrupt.rs), [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs), [`control/legacy.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/legacy.rs), and [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs). This is a static source distinction; no interrupt/restart experiment was run.

### `list_agents` is a loaded-runtime view

The V2 handler returns agent path/name and status, with an optional prefix resolved relative to the caller's agent path. ### Spawn admission and rollback

The V2 spawn path applies more than one resource check. `ensure_execution_capacity` checks the V2 subagent turn-execution limiter; actual turn admission obtains a separate RAII execution guard, held for the admitted task's lifetime. ## V2 child cold-resume configuration

`ensure_v2_agent_loaded` has two materially different resume callers. Both require registered child metadata, a readable stored thread, loadable model-context history, and a resumed history marked V2. They reuse the existing thread ID and rollout; they do not create a replacement child. A caller that supplies the live parent additionally has to prove that the parent is still the same registered running V2 thread in the same runtime registry, and that source/history/stored parent IDs agree.

With a live parent, resume configuration is rebuilt from a fresh parent turn. The child’s stored reasoning effort and stored model/provider are then restored; a saved agent role is reapplied while the current runtime approval policy, cwd, and permission-profile snapshot are preserved. The controller rejects a changed parent execution policy. Cached environment selections must match a currently ready parent environment by environment ID, cwd, and workspace roots. Pending/failed selections are rejected; config differences are rejected after substituting the current owner permission profile. For local executors, a differing cached permission profile is intersected with current owner authority; a remote executor with changed permissions is rejected. This is a constrained resume, not blind restoration of the child’s old authority.

The sender-driven `send_message`/`followup_task` path passes no live parent object to the loader. It retains the supplied resume config, restores stored child model/provider/reasoning, and attempts to inherit environment and execution-policy handles by following the saved `ThreadSpawn` parent source if that parent is loaded. The exec-policy handle is inherited only if the parent/child policy compatibility predicate still passes. This path supplies no `client_mcp_extensions` from a parent object. Parent instructions come from a loaded parent when available, otherwise from the shared thread-instructions provider. Therefore “cold resume” alone does not identify one configuration policy; caller path and which parent/runtime state is available matter.

Sources: [`ensure_v2_agent_loaded`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs), [`inherited_environments_for_source` and `inherited_exec_policy_for_source`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs). ## Multi-agent version selection

In the inspected tag, a configured `features.multi_agent_v2` override selects V2. An explicit global agent disable selects Disabled; otherwise the config override is absent. For a spawned thread, the controller next attempts to inherit the version from its parent/source or the resumed/forked history, and only then falls back to feature configuration (`collab` => V1, otherwise Disabled). ## Interrupted status, completion, and residency

The V2 status mapper classifies both an explicit interrupt abort and a budget-limited abort as `Interrupted`. This status is deliberately non-final for status-wait logic, and completion-message formatting returns no ordinary completion message for `Interrupted`. By contrast, a completed turn can emit a `Completed` activity and a separate queue-only result message. Thus an interrupted child is not equivalent to a completed child whose result is empty.

Residency uses a separate predicate: `Completed`, `Errored`, and `Interrupted` are all unloadable when there is no active turn, durable sleep, or trigger-turn mailbox item. “Not final” therefore does not mean “must stay resident.” Manual interrupt also does not close the persisted spawn edge; a later trigger-turn follow-up can reload the same V2 child if its history and current resume checks pass. These statements describe different state surfaces—agent status, completion delivery, in-memory residency, and graph-edge lifecycle—and should not be collapsed into one done/running label.

The same bundle's shared conversation manager does contain a root-stop cascade. After `interruptConversationSelf` succeeds (or no expected turn ID was supplied), `interruptConversation` schedules descendant cleanup in the background for `user-stop`; other eligible non-follower sources await cleanup. The helper first interrupts active descendants in its current snapshot, then rediscovers the subtree and handles still-active descendants not already processed. It tries a local conversation interruption first; otherwise it reads the most recent turn and sends `turn/interrupt` only when that turn is `inProgress`. Recursive `descendant-cleanup` calls suppress another cascade. Durable `thread/stop` success also triggers descendant cleanup. By contrast, the app-server's matching `turn/interrupt` handler loads only the named thread, validates its active turn ID, and submits one `Op::Interrupt`; it does not traverse descendants. The desktop client cleanup callback runs multiple descendants with `Promise.all`; errors for individual children and discovery failures are logged and do not change the direct per-thread interrupt API contract. Descendants from a snapshot can also change between enumeration and interrupt. The report therefore describes the algorithm's attempts and conditions, not a guarantee every running child is stopped.

The topology owner is `SubagentTopology` in the same app-shared bundle. On the local host it pages `thread/list` with `sourceKinds: ["subAgentThreadSpawn"]`, `useStateDbOnly: true`, and version-appropriate `ancestorThreadId` / `parentThreadId` filters (limit 200). ### SubagentTopology static path

The extracted `app-shared` bundle exposes a store facade: `getSubagentDescendantSnapshot(parentId)` returns currently known descendants, `isComplete: false`, and an `isLoading` flag based on in-flight discovery. Discovery is separate and can reconcile its result with a snapshot of runtime status captured before the asynchronous reads. Full-subtree and direct-child discovery use separate in-flight maps and reuse matching work.

- With thread-list filters supported, discovery queries `thread/list` for `sourceKinds: ["subAgentThreadSpawn"]`, `archived: false`, `sortKey: "created_at"`, descending, `limit: 200`, and `useStateDbOnly: true`. At app-server versions at least `0.143.0-alpha.16`, it uses `ancestorThreadId`; on older versions, it queries each `parentThreadId` and walks descendants. Paging stops at the parent's creation-time boundary and repeated cursors make the result incomplete.
- Without thread-list filters, observed spawn IDs are supplemented from history. `thread/items/list` extracts `subAgentActivity(started)` and `collabAgentToolCall(spawnAgent)` IDs. For a paginated-history thread not yet cached, `thread/turns/list` is scanned page by page to reconstruct child IDs from turn items.
- Candidate children not already known are loaded with `thread/read(includeTurns: false)`. A result is accepted only if its ID matches the requested child and its parent matches the current node. At most two children are fetched concurrently. Failures, identity mismatches, or incomplete nested-history reads preserve `isComplete: false`.
- When a spawn event identifies exactly one child already in the store with a matching parent, the app first hydrates that child in the background and discovers its subtree. Otherwise it falls back to discovering the parent's full descendant set.
- The runtime item-event path calls `discoverForSpawn` when it receives `collabAgentToolCall(spawnAgent)` or `subAgentActivity(started)`. This is an event-driven discovery trigger distinct from the UI's read of the current store snapshot; static code does not establish that opening the panel always launches a fresh query.

These are client-side static observations. The bundle does not reveal server persistence, filtering implementation, authorization, or whether each host uses the same route. `isComplete` describes discovery coverage in this client algorithm; it is not evidence that all remotely existing subagents are known.

### Activity item path into desktop state

Core's `AgentControl::emit_sub_agent_activity` constructs one `TurnItem::SubAgentActivity` and emits `EventMsg::ItemStarted` followed immediately by `EventMsg::ItemCompleted`. In app-server v2, these canonical item events are mapped to typed `item/started` and `item/completed` notifications. The v2 event path explicitly skips the deprecated `EventMsg::SubAgentActivity` lifecycle event; that legacy event remains available to raw-event and rollout consumers. The app-shared notification dispatcher routes the typed notifications to its item handler, which inserts or updates the conversation turn. After processing a completed `collabAgentToolCall(spawnAgent)` or `subAgentActivity(started)` item, it invokes `SubagentTopology.discoverForSpawn`.

The activity item is not limited to creation and completion: the V2 tool handlers emit `started` after spawn, `interacted` after message delivery, and `interrupted` after a successful interrupt request. Completion routing emits `completed` on the initiating thread when it can resolve that initiator, otherwise on the structural parent. It separately routes the completion result to the structural parent as inter-agent communication. Thus an activity is a record in the caller/initiator's turn, while the affected child is identified inside the item; those identities can differ in nested collaboration.

In the installed app-shared projection, `subAgentActivity` becomes a `subagent-activity` UI item with the affected thread ID, a display name derived from the last non-root path segment, `isMessage` true only for `interacted`, and display statuses `started → active`, `interacted → updated`, `interrupted → interrupted`, `completed → completed`. The activity is included only when the host's background-subagents flag is enabled and its `agentPath` passes the current projection filter. This is a presentation mapping, not the authoritative child-thread status; the separate topology/thread snapshot drives the active/done grouping.

This explains the client path from activity emission to state update and descendant discovery. The `started`, `interacted`, `interrupted`, and `completed` business activities are each represented as instantaneous item lifecycles, so protocol item completion must not be read as the child having finished. Completion activity is written into the initiating thread's turn when resolvable (falling back to the structural parent); the child result is delivered separately to the structural parent. No desktop notification stream was captured, and the bundle does not establish server persistence or behavior on every host.

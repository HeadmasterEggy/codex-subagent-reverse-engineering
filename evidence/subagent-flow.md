The selected manager's `user-stop` path can schedule subagent-descendant interruption in the background; this is best-effort cleanup, and the interrupt result or expected-turn guard can affect whether the cascade starts. This is a bundle-level static call graph: no button was clicked and no runtime routing was observed. The Stop control is rendered only when the composer state selects the `stop` submission mode. ### Shutdown request API and ownership boundary (0.162.1 source)

The new public `ThreadManager::request_agent_tree_shutdown(thread_id)` first resolves a **loaded** thread, then closes the exact local runtime's `TaskTracker` admission fence, cancels its shared tree token, closes its mailboxes, and returns an `AgentTreeShutdown` handle. `wait()` and `wait_detailed()` wait until all members admitted before the fence have drained. `admit_start()` checks the closed fence both before and after acquiring a tracker token, so a concurrent start is either tracked by the wait or rejected with `RuntimeShutdown`.

The membership sites inspected cover session startup/session loop, fresh child spawn, agent resume, V2 child loading, legacy completion watcher, resident eviction, and some inter-agent delivery operations. Startup cancellation retains membership until it has stopped session I/O or shut down a partially built session and discarded uncommitted persistence. Teardown guards record abandoned cleanup; detailed reports retain at most 64 failures and count the rest. The ordinary `wait()` surface collapses the report into a generic fatal error; `wait_detailed()` exposes the bounded structured report.

The API explicitly leaves registry removal and caller-owned persistence handoff to its caller. It only fences starts that share the current local runtime; top-level loads/resumes of the same thread ID outside that runtime must be serialized separately. Subagent creation passes the parent's same `LocalAgentRuntime` into the child, so targeting a loaded child ID with this API would resolve the shared runtime and fence the root and its same-runtime siblings too; it is not a child-subtree-only handle. This runtime-wide fence is distinct from `close_agent`: the latter marks the target spawn edge closed and walks the target plus live descendants, shutting them down individually. The inspected app-server idle-thread unload is a third path: it calls `CodexThread::shutdown_and_wait()` for one thread, then removes that same runtime with `remove_thread_if_matches`. A read-only search of the 0.162.1 source found no internal production call site for `request_agent_tree_shutdown` beyond its definition. Thus this tag proves a host/SDK-facing shutdown mechanism exists, not that the ChatGPT desktop invokes it for subagents. This is source inspection only; the API and race behavior were not exercised live. Sources: [`thread_manager/shutdown.rs`](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/thread_manager/shutdown.rs#L105-L147), [`agent/control/runtime.rs`](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/agent/control/runtime.rs#L274-L302), [`codex_delegate.rs`](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/codex_delegate.rs#L81-L130), [`session/startup.rs`](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/session/startup.rs#L32-L105), [`close_agent`](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/agent/control/legacy.rs#L48-L123), and [app-server idle unload](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L419-L489).

## Versioned source path

The public source tag exactly matches the CLI's reported version. In that snapshot:

1. The V2 tool handler builds a `ThreadSpawn` source and sends a `SpawnRequest` to `AgentControl`.
2. `spawn_agent_internal` selects the effective multi-agent version, admits the start, checks capacity, reserves registry/residency slots, and prepares inherited environment/execution policy and metadata.
3. The controller creates the child thread (or forked thread), records the spawn edge, waits for persistence, then submits the first input.
4. On `TurnComplete` or `TurnAborted`, a V2 session constructs an `AgentTurnOutcome` and calls `turn_finished`.
5. Completion routing may emit a `Completed` activity to the initiating thread and queues an inter-agent result communication with `trigger_turn = false`.
6. The parent queue receiving a message and the parent model processing it are separate events.

The older watcher accepts only a `ThreadSpawn` source with a structural parent and only starts while the shared agent-tree runtime admits new work. Its status stream emits an initial snapshot, then coalesced watch-channel updates; it subscribes before reading thread settings so it does not miss an intervening status change. If subscription setup fails or the stream ends/errors before a terminal status is observed, it calls `get_status` once. Final statuses are `Completed`, `Errored`, `Shutdown`, and `NotFound`; `PendingInit`, `Running`, and `Interrupted` are non-final. A tree-shutdown cancellation exits the select, and a `Shutdown` result is suppressed when that same tree shutdown is in progress. Other final results are routed to the structural parent: when an agent path exists and the child is V2, the watcher sends a result communication with `trigger_turn = false`; otherwise it injects `SubagentNotification` without starting a parent turn. Missing parent state or failed path/message construction ends delivery; the V2 send result is intentionally ignored. The watcher holds an agent-tree teardown guard, and an abnormal drop before `complete()` records a shutdown failure. Fresh and resumed spawn callsites both start it only when the effective version is not V2. Sources: [`control.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs), [`control/watch.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/watch.rs), [`status.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/status.rs), [`control/runtime.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/runtime.rs), and [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs). ### Same-tag app-server and state database path

The same source tag also defines the local `thread/list` relation filter. `parentThreadId` and `ancestorThreadId` are mutually exclusive and become direct-child or descendant filters; the app-server passes them through the thread store. The state DB implements descendant lookup with a recursive SQLite CTE over `thread_spawn_edges`, then joins those child IDs to stored threads. `sourceKinds: [SubAgentThreadSpawn]` is mapped to a post-filter over the stored session source. The selected source path's child edge is upserted in the local agent graph store unless the child is ephemeral, and the spawn controller waits for the edge-write task before sending the child's first input. This links edge persistence to the source-level spawn sequence and explains the client bundle's efficient ancestor query. ### Parent result delivery after child termination

In the same source tag, V2 terminal handling has two parent-facing effects with different conditions. A successful child emits `SubAgentActivityKind::Completed` only when its outcome has a `parent_turn_id`; the result communication is then built separately for the parent agent path. The result message has `trigger_turn = false`, so delivery does not by itself start an idle parent turn.

For a loaded parent, the controller submits `Op::InterAgentCommunication` to the session. The session enqueues it in its mailbox and lets the shared pending-work scheduler decide whether to start work; for `trigger_turn = false`, an ordinary idle session is not automatically started. Mailbox delivery can still be accepted into the current active turn while that turn accepts mailbox input. Otherwise the item remains pending and can be collected into later turn input. For an unloaded parent, the controller queues the communication in the local runtime mailbox; the next loaded session takes those messages into its own input queue. Accordingly, successful queue submission proves delivery was accepted or retained, not that the parent model has already consumed the result.

When a parent turn processes the queued `TurnInput::InterAgentCommunication`, the hook path calls `Session::record_inter_agent_communication`. `InterAgentCommunication::to_model_input_item` converts it to a typed `ResponseItem::AgentMessage` carrying author, recipient, and content; the session prepares and records that item in conversation history/rollout and emits the response item. This establishes the source-level handoff from mailbox to model-visible conversation context, while still not proving that a particular live model request sampled that item. Sources: [`hook_runtime.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/hook_runtime.rs), [`session/mod.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/mod.rs), and [`protocol.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/protocol/src/protocol.rs).

The result content is formatted from terminal status: successful output, an error message with bounded error text and next-step guidance, or shutdown/not-found wording; pending, running, and interrupted statuses produce no generic completion message. Special Guardian denial outcomes use a separate instruction. Sources: [`completion.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/completion.rs), [`control.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs), [`mailbox.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/mailbox.rs), [`handlers.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/handlers.rs), and [`input_queue.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/input_queue.rs).

### `send_message` versus `followup_task`

Both V2 tools use one shared handler that rejects whitespace-only messages, resolves the target to a thread ID, builds a resume config from the caller's current turn, sends an `AgentInput::Message`, and emits an `Interacted` activity after the send succeeds. The difference is the delivery mode: `send_message` selects `QueueOnly`, while `followup_task` selects `TriggerTurn`. The target resolution accepts a thread ID directly or resolves an agent reference in the caller's session source. Sources: [`message_tool.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/message_tool.rs), [`send_message.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/send_message.rs), [`followup_task.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/followup_task.rs), and [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs).

For a loaded target, `QueueOnly` submits ordinary inter-agent communication without the trigger flag. The session handler enqueues it and does not ask the pending-work scheduler to start a turn unless the target has an outstanding durable sleep. For an unloaded target, the controller retains queue-only mail in a runtime mailbox; later session loading drains it into the session queue. By contrast, `TriggerTurn` ensures the V2 target is loaded, marks plaintext communication as `NewTask` (or sets the trigger flag on encrypted communication), checks turn-start capacity, and asks the session scheduler to start a regular turn when pending mailbox work is present and the session is idle. Triggered delivery to the root agent is explicitly rejected. Sources: [`delivery.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/delivery.rs), [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs), [`control.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs), [`handlers.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/handlers.rs), and [`tasks/mod.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tasks/mod.rs).

Trigger delivery to an unloaded child uses the existing thread identity and stored history/rollout to resume a V2 session; it does not call the spawn path to create a replacement child. The restore path rejects non-V2 history. If a parent is supplied as owner, it validates that parent is still running, belongs to the same runtime registry, and matches the child's recorded parent; the sender-driven message path passes no parent object and instead restores from the child source and stored configuration/history. Sources: [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs) and [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs).

These paths establish submission and wake policy, not immediate consumption: a queued message can wait for a later turn, and an `Interacted` activity is emitted after accepted delivery rather than after the target model has read the message. This is source-derived behavior for the matching tag; no live child was messaged in this investigation.

### V2 interruption is not closure

The V2 `interrupt_agent` handler snapshots the target first, asks the controller to interrupt it, returns the snapshot's prior status, and emits an `Interrupted` activity. The V2 controller rejects the root and self-targets. If the child runtime is unloaded or already dead, thread-not-found/internal-agent-died errors from the interrupt dispatch are treated as success; this path does not reload the target. It does not mark the persisted spawn edge closed or remove the agent from the registry. In contrast, `close_agent` explicitly marks the edge closed and shuts down the target plus currently live descendants; ordinary shutdown removes runtime/registry/mailbox state but intentionally does not itself close the persisted edge. A later `followup_task` takes the trigger-turn path and ensures the V2 target is loaded before delivery. Sources: [`interrupt_agent.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/interrupt_agent.rs), [`control/interrupt.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/interrupt.rs), [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs), [`control/legacy.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/legacy.rs), and [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs). This is a static source distinction; no interrupt/restart experiment was run.

### `list_agents` is a loaded-runtime view

The V2 handler returns agent path/name and status, with an optional prefix resolved relative to the caller's agent path. The controller gathers metadata from the in-memory agent registry, then includes an entry only if its thread is currently present in the thread manager; known but unloaded agents are skipped, and a root entry is likewise added only when its thread is loaded. The app UI's separate persisted `thread/list` and history-discovery paths therefore have broader historical coverage than this tool result. Sources: [`multi_agents_v2/list_agents.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/list_agents.rs), [`control/api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs), [`control.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control.rs), and [`registry.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/registry.rs).

### Spawn admission and rollback

The V2 spawn path applies more than one resource check. `ensure_execution_capacity` checks the V2 subagent turn-execution limiter; actual turn admission obtains a separate RAII execution guard, held for the admitted task's lifetime. The limiter is initialized from the session's effective V2 agent max-thread setting. Spawn also reserves a registry slot. For V2 resident child sources it first reserves a V2 residency slot and does not pass the ordinary registry max-thread limit to `reserve_spawn_slot`; other spawn paths pass their effective agent max-thread limit to the registry. These controls therefore describe different resources and should not be collapsed into one concurrency limit. Sources: [`execution.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/execution.rs), [`api.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/api.rs), [`tasks/mod.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tasks/mod.rs), [`session/session.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/session.rs), [`spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs), and [`registry.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/registry.rs).

After thread creation, `PendingSpawn` owns the child and tree membership until initial input admission succeeds. If that scope exits before `disarm`, its drop handler schedules cleanup: remove and stop the child, discard its live rollout when available, wait for any pending edge-write task, mark the spawn edge closed, then release membership. An uncommitted registry reservation also releases the count and any reserved path on drop. This is source-described failure cleanup; this investigation did not inject a failure or observe it at runtime. Source: [`spawn_guard.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn_guard.rs) and [`registry.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/registry.rs).

### Child input, configuration, and history modes

The V2 handler turns the supplied `message` into the child's first `AgentInput::Message` and requests `TriggerTurn`. A direct plaintext tool call becomes `AgentMessage::Plaintext`; other tool-call sources become `AgentMessage::Encrypted`. This describes the input type selected by the handler, not whether any downstream transport decrypts or exposes particular content. The handler also passes the current turn's environment snapshot, parent/turn/root IDs, and requested fork mode to the controller. Source: [`multi_agents_v2.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2.rs) and [`multi_agents_v2/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs).

`fork_turns` defaults to `all`; `none` selects a fresh thread, while `all` and any positive integer select `FullHistory`. The integer is accepted for compatibility but does not limit copied turns. V2 rejects legacy `fork_context`. In a fresh thread, the controller may preserve paginated history mode and, only when the V2 dynamic-tools feature is enabled, copies the parent's dynamic tools. In a full-history fork it loads parent model context, filters agent-message items and selected parent-local metadata/instructions, then creates the fork. These branches mean `none` still receives the explicit initial `message`; it means no forked parent history, not no input. Sources: [`spawn.rs` handler](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs) and [`control/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/control/spawn.rs).

Child config is assembled from the live parent turn: current model/provider/reasoning and developer instructions, current approval policy, reviewer, working directory and permission-profile snapshot. Requested or configured default subagent model/reasoning can override those values after model-catalog validation. A selected role is then applied as a constrained config overlay: it may supply instructions/model/personality/service tier and disable selected features or skills, but the implementation comment says roles cannot replace parent authority. For a full-history V2 fork, role application is skipped unless a role was explicitly named; V2 supports that explicit override while V1 rejects it. Source: [`child_config.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/child_config.rs) and [`role.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/role.rs).

This is source analysis at the matching public tag. It does not establish the resolved settings or exact inputs of a live child session.

Tool availability is also not copied as one opaque parent registry. Session startup materializes the selected child dynamic-tool snapshot into session configuration; each turn then builds a tool router from the child's turn config, environment snapshot, MCP binding, extensions, and dynamic tools. Role overlays only carry feature disables for the listed shell, apps, plugins, memory, and request-permissions features; they do not apply role feature enables. This supports the narrower conclusion that part of the tool surface is rebuilt under child config and policy, while V2 dynamic tools have an explicit gated inheritance path. It does not establish the exact tools exposed by any live child, since those depend on runtime config, MCP/extensions, model, and feature state. Sources: [`session/mod.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/mod.rs), [`session/turn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/session/turn.rs), [`tools/spec_plan.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/spec_plan.rs), and [`agent/role.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/role.rs).

The model-facing V2 tool schema requires `task_name` and `message`; optional fields and even `agent_type` / model override exposure depend on `SpawnAgentToolOptions`. The role description is generated from configured user roles followed by built-ins, and can append model/reasoning settings marked as non-overridable. There is a small contract mismatch worth documenting: the `fork_turns` description says only `all` and `none` are supported, while the runtime parser also accepts any positive integer and maps it to full-history fork without limiting turns. The schema models it as a string, so the narrower wording is descriptive rather than an enum validation. Sources: [`multi_agents_spec.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_spec.rs), [`role.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/agent/role.rs), and [`multi_agents_v2/spawn.rs`](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs).

## V2 child cold-resume configuration

`ensure_v2_agent_loaded` has two materially different resume callers. Both require registered child metadata, a readable stored thread, loadable model-context history, and a resumed history marked V2. They reuse the existing thread ID and rollout; they do not create a replacement child. A caller that supplies the live parent additionally has to prove that the parent is still the same registered running V2 thread in the same runtime registry, and that source/history/stored parent IDs agree.

With a live parent, resume configuration is rebuilt from a fresh parent turn. The child’s stored reasoning effort and stored model/provider are then restored; a saved agent role is reapplied while the current runtime approval policy, cwd, and permission-profile snapshot are preserved. The controller rejects a changed parent execution policy. Cached environment selections must match a currently ready parent environment by environment ID, cwd, and workspace roots. Pending/failed selections are rejected; config differences are rejected after substituting the current owner permission profile. For local executors, a differing cached permission profile is intersected with current owner authority; a remote executor with changed permissions is rejected. This is a constrained resume, not blind restoration of the child’s old authority.

The sender-driven `send_message`/`followup_task` path passes no live parent object to the loader. It retains the supplied resume config, restores stored child model/provider/reasoning, and attempts to inherit environment and execution-policy handles by following the saved `ThreadSpawn` parent source if that parent is loaded. The exec-policy handle is inherited only if the parent/child policy compatibility predicate still passes. This path supplies no `client_mcp_extensions` from a parent object. Parent instructions come from a loaded parent when available, otherwise from the shared thread-instructions provider. Therefore “cold resume” alone does not identify one configuration policy; caller path and which parent/runtime state is available matter.

## Interrupted status, completion, and residency

The V2 status mapper classifies both an explicit interrupt abort and a budget-limited abort as `Interrupted`. This status is deliberately non-final for status-wait logic, and completion-message formatting returns no ordinary completion message for `Interrupted`. By contrast, a completed turn can emit a `Completed` activity and a separate queue-only result message. Thus an interrupted child is not equivalent to a completed child whose result is empty.

Residency uses a separate predicate: `Completed`, `Errored`, and `Interrupted` are all unloadable when there is no active turn, durable sleep, or trigger-turn mailbox item. “Not final” therefore does not mean “must stay resident.” Manual interrupt also does not close the persisted spawn edge; a later trigger-turn follow-up can reload the same V2 child if its history and current resume checks pass. These statements describe different state surfaces—agent status, completion delivery, in-memory residency, and graph-edge lifecycle—and should not be collapsed into one done/running label.

### Activity item path into desktop state

Core's `AgentControl::emit_sub_agent_activity` constructs one `TurnItem::SubAgentActivity` and emits `EventMsg::ItemStarted` followed immediately by `EventMsg::ItemCompleted`. In alpha.20, a per-session resident queue is touched on access and appends the touched thread at the back. ## Spawn admission versus child turn task start in alpha.9

The initial `TriggerTurn` communication is submitted after `spawn_child_thread` has returned a registered child runtime. #### Snapshot freshness and reconciliation

The same bundle separates the synchronous store snapshot from completed discovery. `getKnownSubagentDescendantThreads(parent)` combines thread summaries with loaded thread records, then follows each candidate's parent chain to include known descendants; it only returns records available in `threadsById`. `SubagentTopology.getSnapshot(parent)` wraps that view with `isComplete: false` and sets `isLoading` when a full or direct-child discovery for that parent is in flight. ## Child capabilities do not depend on copied history in alpha.9

The later `rust-v0.163.0-alpha.9` snapshot also changes how a spawned child receives startup capabilities. Commit [`845345b1dd4f8e2a5d5ce91363fff666e41b07fc`](https://github.com/openai/codex/commit/845345b1dd4f8e2a5d5ce91363fff666e41b07fc) replaces separate fresh-thread and fork-thread startup branches with shared `StartThreadOptions`, captured from the spawning turn before history is prepared ([spawn path](https://github.com/openai/codex/blob/4753ce3d19df9ffa58353736c4ffde49ed071589/codex-rs/core/src/agent/control/spawn.rs#L686-L845)). The parent is resolved from the session source first, with the explicit parent option as fallback. If `disabled_plugin_ids` is omitted, the child inherits the parent's current list; an explicit list, including an empty list, overrides it.

Selected capability roots are a separate setting from the disabled-plugin list. At shared session startup, explicit roots win, including an explicit empty list. Otherwise, a non-resumed child with `SessionIsolation::Inherit` takes roots from its inherited environment snapshot even when its conversation history is fresh or forked. A resumed thread instead restores its saved roots from history; isolated startup does not inherit the parent's environment roots ([session startup](https://github.com/openai/codex/blob/4753ce3d19df9ffa58353736c4ffde49ed071589/codex-rs/core/src/session/mod.rs#L647-L671)). Regression-test source covers explicit-root precedence, empty roots, inherited versus isolated startup, history persistence, and fresh/forked plugin-choice overrides ([startup tests](https://github.com/openai/codex/blob/4753ce3d19df9ffa58353736c4ffde49ed071589/codex-rs/core/src/thread_manager_tests.rs#L1953-L2098), [plugin-choice tests](https://github.com/openai/codex/blob/4753ce3d19df9ffa58353736c4ffde49ed071589/codex-rs/core/src/agent/control_tests.rs#L2271-L2328)). The app-server test also exercises executor skill listing/reading and plugin MCP registration for `fork_turns: "none"` and `"all"` ([test source](https://github.com/openai/codex/blob/4753ce3d19df9ffa58353736c4ffde49ed071589/codex-rs/app-server/tests/suite/v2/executor_skills_spawn_tests.rs#L27-L242)). These are source tests; none were run here.

This narrows the earlier statement that fresh and forked children may receive different capabilities: history mode alone does not select the startup capability roots or omitted plugin-disable choices in this snapshot. The inheritance remains conditional on the inherited environment snapshot and isolation policy, and it does not mean the child receives the parent's entire tool registry. This is later public source, not runtime evidence for the installed `0.162.0-alpha.17.2` desktop CLI.

## Alpha.10 comparison boundary

The GitHub compare between `rust-v0.163.0-alpha.9` (`4753ce3d19df9ffa58353736c4ffde49ed071589`) and `rust-v0.163.0-alpha.10` (`cd643519fb56011557d09b41053a3a4c0e013e1f`) reports `diverged` (12 commits ahead, 1 behind). These were considered because their paths matched the broad scan; neither provides evidence of changed child scheduling.

One broader capability-related change deserves a precise boundary. Commit [`703d253ed676c26e4b9708a374b7344b5c1bcc53`](https://github.com/openai/codex/commit/703d253ed676c26e4b9708a374b7344b5c1bcc53) wires `capabilities/discoverV2` through the exec-server RPC: initialized remote sessions advertise support, `Environment::discover_capabilities_v2` checks that support, executor-side discovery is refreshed according to watcher registration and sandbox context, and requests are replayed after executor recovery. Its integration test checks metadata refresh, omission of skill instruction bodies, and sandbox separation ([RPC test](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/exec-server/tests/capabilities_v2.rs#L1-L214)). In the inspected alpha.10 source, this exact `discover_capabilities_v2` method remains confined to exec-server and its tests; no core/app-server caller was found.

That negative result does **not** mean core skips executor capability discovery. The model-step path resolves selected roots, calls `executor_capability_discovery_for_step`, places the resulting `ExecutorCapabilityDiscoverySnapshot` in step extension data, and passes it to selected-plugin projection and `turn::built_tools` ([step preparation](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/core/src/session/mod.rs#L3919-L4008)). The cache behind this path calls the distinct `Environment::discover_capability_roots` API ([cache](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/exec-server/src/capability_discovery_cache.rs#L128-L220), [environment API](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/exec-server/src/environment.rs#L1062-L1093)). `SkillsExtension::tools_for_step` reads that snapshot and selected roots to build executor skill tools; the executor provider projects discovered skill metadata/instructions into the catalog and reads a selected skill through the environment filesystem ([skill tool assembly](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/ext/skills/src/extension.rs#L282-L322), [executor provider](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/ext/skills/src/provider/executor.rs#L82-L220)). The app-server spawn test exercises a child listing and reading an executor skill and checks plugin MCP registration with both `fork_turns` modes, and with the plugin enabled/disabled ([spawn test](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/app-server/tests/suite/v2/executor_skills_spawn_tests.rs#L27-L242)). Thus selected-root V1 discovery does feed the child-visible skill/plugin path in this source snapshot; the separate V2 RPC's use in child tool assembly is not established. These are source links and test assertions; no tests were run and this does not establish the installed desktop client's runtime behavior.

The source also closes the “catalog versus model-visible tool” gap. `SkillsExtension::tools_for_step` returns `skills.list` and `skills.read` only when cloud skills are enabled or the step has a nonempty executor-root query ([tool construction](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/ext/skills/src/tools/mod.rs#L59-L91)). `core::tools::spec_plan::built_tools` obtains each contributor's step tools, wraps and registers them subject to tool policy, then `build_model_visible_specs` keeps only directly exposed tools; `build_prompt` supplies that visible-spec list to the model ([registration](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/core/src/tools/spec_plan.rs#L145-L180), [visibility filter](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/core/src/tools/spec_plan.rs#L627-L646), [prompt assembly](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/core/src/session/turn.rs#L1615-L1635)). Thus this source establishes the route by which child skill tools can reach the model, while tool policy, exposure/mode, and availability gates remain material conditions; the child spawn tests establish exercised calls in their test fixtures, not universal availability in every live child.

Plugin MCP registration is a parallel path with separate gates. The step resolver considers only contributors matching ready selected roots, then omits a plugin when the Plugins feature is off, the plugin configuration disallows it, or its ID is in the child's disabled list ([per-step plugin selection](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/core/src/mcp.rs#L191-L225)). The MCP projection builds registrations from selected-plugin contributions, omits disabled servers, and installs the resulting registrations in the MCP server catalog ([plugin MCP projection](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/core/src/mcp.rs#L252-L289), [catalog construction](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/core/src/mcp.rs#L396-L456)). So selected roots are shared input, but skill list/read availability and plugin MCP registration are not the same mechanism or controlled by identical gates.

The paths meet again when the executor skill catalog is projected. `SkillsExtension::tools_for_step` gives the skill tools both the executor query and the step's `SelectedPluginSnapshot`; before returning the executor catalog, the skill tool context applies `attribute_executor_plugins`. That function removes skills whose root is in `disabled_plugin_roots`, and attaches the selected plugin ID to skills under enabled plugin roots ([step wiring](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/ext/skills/src/extension.rs#L286-L317), [catalog filtering and attribution](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/ext/skills/src/tools/mod.rs#L231-L245), [projection function](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/ext/skills/src/provider/executor.rs#L68-L84)). Consequently, a disabled plugin affects both its MCP registration and the skill entries associated with that selected root; this is a source-level behavior in alpha.10, not a live-child observation.

The app-server spawn test asserts both sides of this behavior for the parent and child. With the plugin disabled, each agent's skill list is empty, its read result omits the skill body, and its MCP status omits the plugin server. With the plugin enabled, each reads the expected contents from the selected root, lists `spawn-plugin:deploy`, and sees the plugin MCP server; the test also asserts that the parent and child catalogs match. Its four cases cross `fork_turns: "none"`/`"all"` with enabled/disabled plugin selection ([test setup and matrix](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/app-server/tests/suite/v2/executor_skills_spawn_tests.rs#L27-L38), [assertions](https://github.com/openai/codex/blob/cd643519fb56011557d09b41053a3a4c0e013e1f/codex-rs/app-server/tests/suite/v2/executor_skills_spawn_tests.rs#L202-L255)). These are assertions in the source test; the test was not run for this report and does not establish what a live desktop child received.

These checks broaden the earlier path-filter result; they do not prove that no other alpha.10 change can indirectly affect child behavior. They also do not establish behavior in the installed desktop CLI (`0.162.0-alpha.17.2`).
